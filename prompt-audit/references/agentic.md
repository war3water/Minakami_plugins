# Agentic prompts — guidance for tool-using agents

Read this file when the prompt under audit drives a tool-using agent: system prompts or agent instructions with tools, runbooks, long-running or unattended runs. Cite as `[ref: agentic.md §<section>]`. Everything here holds across vendors; agentic guidance for one provider or model is in that provider's file under `providers/`.

## Universal

- **Completion criteria and evidence-backed status.** State what done means — which checks must pass, which artifacts must exist — and require progress claims to point at tool results from the session. Without a stated completion condition the model picks its own stopping point; without the evidence rule, status reports drift from what was verified. When done means a test passes — whether the prompt says so or only the user's success criteria do — the prompt must say whether the test itself may be changed: otherwise the cheapest green run is editing, skipping, or weakening the test.
- **Autonomy boundaries.** Say which actions the model may take freely (local, reversible) and which need confirmation (destructive, hard to reverse, visible to others, scope expansions). Without the boundary the model over-asks and stalls, or takes unrequested actions; blanket caution language produces the stall.
- **Approval and absolute rules, as written.** Current models apply an approval rule to exactly what it names, so name the actions it covers: a broad category ("anything that reaches people outside this conversation") also holds back routine work it was not meant to cover. A rule containing "never" is read as absolute, so write the exception into the rule itself — "ask for approval before deleting files", not "never delete files" — and give other absolute rules their scope and reason. A general "act more freely" is too vague to move a model that follows such rules closely; list the routine steps it may take on its own. Stop conditions in validation or review steps ("stop and review at the first error") block autonomous work the same way; keep only the ones the task needs. Such rules pile up in the memory, notes, and instruction files an agent carries between sessions and outlive their reason; audit them there too when that file is the prompt under audit.
- **Persistence and obstacles.** Text that tells the agent to keep going should separate ordinary obstacles — errors, timeouts, empty results, a failing tool: diagnose them and work through them — from deliberate blockers — a file marked not to be touched, withheld access, a guardrail: leave them alone and report. Without the split the agent either stops at the first timeout or works past a deliberate block. Persistence text lowers how often the agent asks, so the confirmation rule for risky or irreversible actions must still stand beside it.
- **A final report for a cold reader.** Whoever reads the final report of a long run has not seen the tool calls, files, or progress updates behind it. Ask for a report that stands on its own — what was found, what was done, what is left — without working shorthand carried over from reasoning, tool calls, or subagent briefs. Unasked, the report reads as the tail of notes the reader never saw.
- **The prompt under audit as a runbook.** Say what the agent does with an unclear request — ask, or proceed under a stated assumption — and with instructions that arrive inside tool results or data (inert unless the harness says otherwise).
